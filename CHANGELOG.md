# Changelog

## Unreleased

- Widen the secret file names the read-only agent tools refuse, and stop matching excluded directories by case (follow-up to the case fix above). Before, `read_file` and `search_project` refused only six exact names, so `id_rsa.txt`, `credentials.yaml`, `secrets.json`, `service-account.json`, `kubeconfig.yaml`, `server.key.txt`, `prod.env.txt` and `prod.tfvars.json` were readable, and `Node_Modules/x.py` passed because the excluded directory names were compared case-sensitively. A path part that ends in a dot or space or holds a colon (Windows aliases and alternate data streams such as `node_modules.` and `credentials.json:x.json`) is now refused too. The policy is a lower-case exact name set plus a few `fnmatch` patterns anchored at the start or end of the name, in `agent_loop.py`, and names such as `environment.md`, `key_manager.py`, `keys.md` and `secrets_policy.md` stay readable. Hidden names, `.npmrc`, `.netrc` and `.env.*` were already refused by the hidden-name rule and are now named in the policy as well. Names such as `gcp-key.json` that match no pattern are still readable, so this stays a name policy and not a secret scanner. Covered by `tests/unit/test_read_tool_protected_names.py`, with a mutation check of each rule.
- Treat a contained-process registry row with no recorded start token as unconfirmed, and refuse rows that name the host process on Windows (finding of the independent review of worker isolation). Before, a row written when the process identity could not be read at spawn was reported as `identity_mismatch` once its process id was alive, which does not block the task, so a possibly live worker was treated as safe. Now the reaper sends no signal, marks the row `unconfirmed` and blocks the task. A row whose process id is the host's own or below 2 is now refused on Windows as it already was on POSIX, before any `taskkill`. Registry rows are still not authenticated, and `site_docs/worker-containment.md` records what that does and does not cover. Covered by `tests/unit/test_registry_row_trust.py`, which uses real processes on POSIX and fakes for the Windows decision logic, and nothing here was run on Windows or macOS.
- Harden the Windows job object name and creation in worker containment. Before, `CreateJobObjectW` was called without checking for `ERROR_ALREADY_EXISTS`, so a job object that already had the name was adopted and given the worker's limits, and the name accepted any caller-supplied id. Now creation fails closed when the name exists and releases its handle without changing that object, the name is built only from the registry's random `cp_` plus 32 hex id (spawn refuses any other id, and the orphan reaper never opens a name from a stored id of another shape), and the last error is cleared before the call. The handle stays non-inheritable. Covered by `tests/unit/test_windows_job_name.py` with a fake kernel32, plus two skipped-unless-Windows tests. This was not run on Windows by its author, so the Windows CI jobs are the first real evidence, and the module caveat about unverified macOS and Windows paths still applies.
- Protect agent instruction files in every directory and environment files, and compare secret file names without regard to case in the read-only agent tools (findings of the independent review of worker isolation, issue 28). Before, the patch policy blocked `AGENTS.md` and `CLAUDE.md` only at the repository root, so a patch could rewrite `sub/AGENTS.md` and steer an agent that reads it, and it did not block `.envrc` or files such as `secrets.env`. `**/AGENTS.md`, `**/CLAUDE.md`, `.envrc`, `**/.envrc`, `*.env` and `**/*.env` are now protected. The `read_file` and `search_project` tools compared the secret names `credentials.json`, `id_rsa` and `id_ed25519` case-sensitively, so `Credentials.json` was readable. They now compare in lower case. The earlier test that listed `src/Claude.md` as an ordinary path now uses `src/Claude_notes.md`.
- Match protected patch paths without regard to case (finding of the independent review of worker isolation, issue 28). Before, `check_path` matched them with `fnmatch.fnmatch`, which follows the host operating system, so on Linux `.GitHub/Workflows/ci.yml`, `agents.md`, `.ENV` or `Private.PEM` passed the check, and on a filesystem that ignores case (macOS, Windows) they name the protected files. Paths and patterns are now compared in lower case with a case-sensitive match, so the policy is the same everywhere. A path component that ends in a dot or a space, or contains a colon, is rejected, because Windows drops the trailing dot or space (`.git.`, `AGENTS.md `) and a colon starts an alternate data stream, and acceptance contracts reach this check without the diff header's character filter, and two spellings of one file in a patch count as a duplicate. The caller's allowlist is still matched case-sensitively, which can only make it stricter.
- Bound the output the Docker sandbox reads from the container CLI (finding of the independent review of worker isolation, issue 28). Before, a test that printed without limit filled host memory until the time limit, because the CLI's whole output was collected in memory. Now the output is hashed as it arrives and never stored, so receipts keep the same hashes. Past 128,000 bytes the receipt is still flagged as truncated. Past 4 MiB on both streams together the CLI is killed, the container is removed by name and the receipt has no exit code and is flagged as truncated. The two reader threads are finished before the run returns. A reader that is still blocked because another process holds the pipe, or that failed on a read error, marks the receipt as truncated, and a blocked reader leaves its stream open so a closed and reused file descriptor cannot be read. A run that outlasts its time keeps the output hashed so far. The new tests run real child processes in place of the CLI, including a run that never stops printing, an interrupt, a slow reader and a pipe held by another process.
- Run the host-side Git calls of the coding workflow against the source repository's own metadata directory for the worktree, not the `.git` entry inside the worktree (finding of the independent review of worker isolation, issue 28). The Docker runner mounts the worktree read/write, so test code can replace that entry, and Git would then read a config the host does not control. `worktree_git_dir` finds the directory from the repository's `worktrees/*/gitdir` files (absolute or relative pointers), refuses zero or several matches and reports a missing worktree as a `WorkspaceError`. `git status`, `git add -N`, `git diff`, `git apply`, the file-mode check and the line-ending lookup pass `--git-dir`, `--work-tree`, `--literal-pathspecs` and `core.fsmonitor=false`. `git status` also ignores submodules, because Git would otherwise run a clean filter from a nested repository planted under a gitlink path. The patch-step Git calls now use the same scrubbed environment as the other Git calls, so a filter from the user's global config cannot be selected by a `.gitattributes` the container wrote, and the user's line-ending settings are forwarded explicitly. After the tests the host also checks that `<worktree>/.git` is still the original pointer file. If not, the run is recorded as `workspace_integrity_failed`. A worktree left that way still has to be removed by hand. Regression tests in `tests/security/test_worktree_trusted_git.py` plant a replacement `.git`, a clean filter and a nested repository, each with a control that shows the unprotected call runs it. This covers the Git calls of the coding workflow on a worktree. It does not cover other host processes, and it does not make the Docker sandbox itself certified.
- Remove the Docker sandbox container on every exception exit, not only on timeout, and add `--memory-swap` equal to `--memory` and `--log-driver none` to its options (finding of the independent review of worker isolation, issue 28). Before, an interrupt, a memory error or an OS error ended with Python killing the Docker CLI, which does not stop the container, and the daemon also kept its own copy of everything the test printed. The cleanup runs `rm -f` on the run's container name, notes on the original error when the container may still be running, and never hides that error. It does not help if the Python process itself is killed. On a host without swap accounting, Docker may print a swap-limit warning that changes `stderr_sha256`. The argument-list allowlist test now includes the two new options.
- Check the argument list of the Docker sandbox for host access (part of issue 20, which stays open). The real isolation probe cannot see a bind of a tmpfs-backed host directory such as `/dev/shm`, because it looks like tmpfs from inside the container. `tests/security/test_code_sandbox.py` now reads the `docker run` arguments the runner builds and compares them with an allowlist of exactly the options the runner emits. Every value is compared exactly with what the runner is configured to emit (a limit of 0 or a group of 0 does not pass), except the container name, which carries a hash of the command and is matched by pattern. Anything else before the image name fails, including an unknown option, a bundled short option such as `-itv`, an inline `--flag=value` form, a stray positional token, a repeated option, a missing required option, a different binary, and an option before `run` that selects another daemon. What comes after the image name is the test command and is not checked. Forty-seven extra options, four daemon-selecting prefixes, a removal of each of the fifteen required options and twenty-two value and structure controls are each expected to be flagged with the offending token named. This does not see a mount the daemon adds on its own, so the in-container probe is still needed and the tmpfs-backed bind gap in it is still open. It runs without a Docker daemon.

- Fix `database is locked` under slow disks. SQLite's busy handler is not fair, so with several writer threads one could lose the race for longer than the busy timeout, which failed the bounded state stress step on a Windows runner. `SQLiteRepository` now queues threads of one process per database file in arrival order and keeps SQLite's busy timeout for contention between processes (`busy_timeout_seconds`, default 10, and `queue_patience`, default 3 times that for threads waiting in the queue). A waiter whose turn does not come within that limit still gets `database is locked`, so a holder that never releases cannot hang anyone. Writers wait in that queue and so can wait up to 30 seconds instead of about 10. The repository's own pure read methods skip the queue, because under WAL a read does not wait for a writer. Reads made elsewhere through `_connection()` still queue. Reproduced locally with 60 ms commits before the fix and covered by `tests/unit/test_storage_fair_lock.py`. Repeated on real Windows Server 2022 and 2025 runners, where the old code failed some heavy stress runs with `database is locked` and the version before the read-skips-queue change failed none of 40 (details and limits in PR 14).

## 0.13.0a1 — experimental alpha

Local decision records and transfer policies; bounded read-only agent execution; consent-bound coding and review; SQLite workflow coordination, backups and migration; loopback web API; read-only MCP and editor clients; reproducible package tooling.

Platform, isolation and security limitations are documented in the user guides and SECURITY.md. No stable release or production certification is claimed.
