## Unreleased

- Check the argument list of the Docker sandbox for host access (part of issue 20, which stays open). The real isolation probe cannot see a bind of a tmpfs-backed host directory such as `/dev/shm`, because it looks like tmpfs from inside the container. `tests/security/test_code_sandbox.py` now reads the `docker run` arguments the runner builds and compares them with an allowlist of exactly the options the runner emits, each with the one value it emits. Anything else before the image name fails, including an unknown option, a bundled short option such as `-itv`, an inline `--flag=value` form, a stray positional token, an option before `run` that selects another daemon, a repeated option, and a missing required option. What comes after the image name is the test command and is not checked. Forty-seven extra options, four daemon-selecting prefixes, a removal of each of the fifteen required options and four value controls are each expected to be flagged with the offending token named. This does not see a mount the daemon adds on its own, so the in-container probe is still needed and the tmpfs-backed bind gap in it is still open. It runs without a Docker daemon.

Tested on synthetic human files only, so no result in it is a human result.

- Fix `database is locked` under slow disks. SQLite's busy handler is not fair, so with several writer threads one could lose the race for longer than the busy timeout, which failed the bounded state stress step on a Windows runner. `SQLiteRepository` now queues threads of one process per database file in arrival order and keeps SQLite's busy timeout for contention between processes (`busy_timeout_seconds`, default 10, and `queue_patience`, default 3 times that for threads waiting in the queue). A waiter whose turn does not come within that limit still gets `database is locked`, so a holder that never releases cannot hang anyone. Writers wait in that queue and so can wait up to 30 seconds instead of about 10. The repository's own pure read methods skip the queue, because under WAL a read does not wait for a writer. Reads made elsewhere through `_connection()` still queue. Reproduced locally with 60 ms commits before the fix and covered by `tests/unit/test_storage_fair_lock.py`. Repeated on real Windows Server 2022 and 2025 runners, where the old code failed some heavy stress runs with `database is locked` and the version before the read-skips-queue change failed none of 40 (details and limits in PR 14).
- Fix a race in `inspect_database` (behind `dbound state check`, and also run by backups, restores and migrations). It asked whether the `-wal` file existed and then read its size, and SQLite deletes that file when the last connection closes, so a concurrent writer could make the second step raise `FileNotFoundError`. It was seen once as a failure of `test_workload_bounds_and_integrity` in CI. The size is now read directly and a missing file counts as 0. Covered by a test that makes the file vanish between the two steps, which fails on the old code.
